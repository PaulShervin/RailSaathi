## 1. Objectives
- Integrate RailRadar API (`https://api.railradar.in`) for real Indian Railways train timetables and journey-specific fares.
- Implement resilient `RailRadarClient` adapter covering:
  - `GET /v1/trains/between/{from}/{to}`
  - `GET /v1/lookup/search/stations`
  - `GET /v1/trains/{number}/fare`
- Implement `TrainDataProvider` interface with `RailRadarTrainDataProvider` (live) and `MockTrainDataProvider` (offline/tests).
- Implement tiered thread-safe in-memory caching (`RailRadarCache`) with category-specific TTLs (stations: 24h, schedules: 1h, fares: 30m).
- Implement bounded candidate fare enrichment (capped by `RAILRADAR_MAX_FARE_LOOKUPS_PER_REQUEST = 5`) to protect request budgets.
- Add `GET /api/stations/search` endpoint and frontend station autocomplete support.
- Ensure strict secret redaction (no credentials in logs, errors, or git).
- Expand test suite to 90 automated tests (100% passing) and add standalone live smoke test suite.

## 2. Key Changes & Implementations

### RailRadar Client Adapter (`Ticketing_Guidance_Module/backend/journey/railradar_client.py`)
- Created `RailRadarClient` handling HTTP communication via `requests.Session` with connection pooling.
- Implemented `Authorization: Bearer <RAILRADAR_API_KEY>` header construction and URL parameter validation.
- Added strict typed error hierarchy: `RailRadarBadRequestError` (400), `RailRadarAuthError` (401/403), `RailRadarNotFoundError` (404), `RailRadarRateLimitError` (429 with `Retry-After`), `RailRadarUnavailableError` (503), `RailRadarNetworkError`, and `RailRadarSchemaError`.
- Added bounded exponential retry for transient 500/502/503/504 errors and socket timeouts (max 1 retry), strictly avoiding retries for 400, 401, 404, or 429.
- Built thread-safe tiered cache `RailRadarCache` with LRU-like eviction.
- Built internal metrics tracker (`train_searches_made`, `station_searches_made`, `fare_lookups_made`, `cache_hits`, `api_errors`).

### TrainDataProvider Abstraction (`Ticketing_Guidance_Module/backend/journey/timetable.py`)
- Created abstract `TrainDataProvider` base class.
- Implemented `RailRadarTrainDataProvider` with response normalization:
  - Day-offset calculation (`from_day` vs `to_day` or overnight time rollover heuristic).
  - Duration normalization (`parse_duration_to_minutes`).
  - Typed models: `FareQuote` and granular `FareBreakdown` (base fare, reservation charge, superfast charge, catering, GST).
- Implemented `MockTrainDataProvider` using the verified offline corridor database.
- Implemented `TrainSearchService.enrich_candidate_fares` to query fares only for top shortlisted candidates for the passenger's requested class and quota.

### Configuration & Secret Handling (`backend/config.py` & `.env.example`)
- Added `TRAIN_DATA_PROVIDER` selection (`railradar` vs `mock`).
- Added `RAILRADAR_API_KEY`, `RAILRADAR_BASE_URL`, `RAILRADAR_TIMEOUT_SECONDS`, `RAILRADAR_MAX_RETRIES`, `RAILRADAR_MAX_FARE_LOOKUPS_PER_REQUEST`, and cache TTL configurations.
- Dual `.env` loading from root and module directory.

### API & Frontend Integration (`backend/app.py` & `frontend/src/App.jsx`)
- Added `GET /api/stations/search` endpoint for debounced station search.
- Updated `GET /api/health` to report active provider (`train_data_provider`) and configuration status.
- Updated React UI to render overnight day offsets (`+1d` pill), fare quotas (`GN Quota`), and retrieval timestamps.
